What is Node.js?

The JavaScript runtime — V8 + libuv + a core library.

One of the most depended-on projects in the world, built and maintained by volunteers.

Keep this short. Enough to say: it's big, it's foundational, and it's people — not a company — who keep it running. That's why you being here matters. V8 runs the JS, libuv is the async/event-loop + I/O layer, and the core library (lib/) is the JS APIs everyone imports.

It's all one GitHub repo.
nodejs/node

Demystify it. The thing that runs half the internet is a repo you can fork right now. No special access required to contribute.

How a contribution lands

fork→ branch→ commit -s→ pull request→ CI→ review→ a collaborator lands it

Nobody pushes to main. Every change is a PR, reviewed, and landed for you.

Walk the pipeline once. The two surprises for newcomers: commits are signed off (DCO, `-s`), and you don't merge your own PR — a collaborator lands it with git node land after review and green CI. Reassure: CI is big and sometimes flaky. That's normal, not you.

Who reviews and lands

  • Collaborators — review and land PRs
  • Subsystem teams — own an area, get pinged on it
  • TSC — technical stewardship, tie-breaks

Landing needs approvals + green CI + a waiting period. Then git node land.

The point: there's a human process behind every merge, and it's open — anyone can become a collaborator by showing up and helping consistently. Don't overstate the exact rules (approvals/48h) — the audience just needs the shape.

Node is organized into subsystems

  • doc/

    Docs & guides — the friendliest start

  • test/

    The test suite — coverage & flakes

  • lib/

    The JS core APIs

  • src/

    C++ internals & bindings

  • deps/

    V8, libuv, and friends

  • build/ tools/

    Build system & automation

PRs are labeled by subsystem, and the label pings the team that owns it — say that out loud. The commit subject encodes it too: `doc: fix typo`. Two takeaways: (1) the repo isn't a monolith you must understand whole — pick one area; (2) doc, test, and lib are where most first contributions live and where review is most welcoming.

Where to find work

  • good first issue the label built for today
  • help wanted maintainers are asking for hands
  • docs & tests always something to improve
  • flaky tests find one, make it reliable
These are the reliable veins. `good first issue` is curated for events like this. Docs and tests never run out and rarely need C++.

The best issue is
the one you just hit.

A confusing doc, a rough error message, a missing test — that's a contribution.

Sustainable sourcing: stop waiting for a curated list. Use Node, notice friction, fix it. That's how most collaborators started, and it scales past today.

Contributions aren't just code

The project also needs

  • Reviewers
  • Issue triagers
  • Docs & translations
  • Test & CI wranglers
  • People answering questions

Why it matters

Triage and review are the bottleneck, not patches. Helping here is how you learn the codebase — and the path to becoming a collaborator.

Reframe "contributor" beyond code. For many people, triaging issues or reviewing is a better on-ramp than a first patch — and it's what the project needs most.

Using AI, responsibly

Appropriate

  • Learn the codebase, explain unfamiliar code
  • Draft an approach you then read and own
  • Help write tests, docs, commit messages

Inappropriate

  • Bulk, low-effort AI-generated PRs
  • Submitting code you don't understand
  • Pasting output you haven't verified

You are accountable for your contribution. Understand it, test it, and disclose AI use.

Draft framing — check against the current Node.js / OpenJS AI policy before the event and update wording to match it exactly. The spirit: AI is a fine tool for learning and drafting; it is not a way to mass-produce PRs a human hasn't understood. Maintainer time is the scarce resource we're protecting.

Your first PR

# branch off an up-to-date main
git checkout -b my-first-contribution

# make the change, then commit with DCO sign-off
git commit -s -m "doc: fix typo in fs.read docs"

# build & test what you touched
make -j4 && make test

# push to your fork, then open a PR against nodejs/node
git push origin my-first-contribution

Commit subject: subsystem: lowercase summary, under ~50 chars. -s is required.

The two things newcomers miss: DCO sign-off (`-s`) and the `subsystem: summary` commit format. Everything else a mentor can walk them through. You don't need the whole test suite — run the tests relevant to your change. Doc-only changes don't need a build.

While you work

  • Ask early — that's what mentors are for
  • Small & focused beats big & sprawling
  • CI is large and sometimes flaky; be patient
  • Review takes time — landing may be after today
Manage expectations for after the event: a PR opened today may land next week. That's success. Encourage them to keep watching the PR and responding to review.
