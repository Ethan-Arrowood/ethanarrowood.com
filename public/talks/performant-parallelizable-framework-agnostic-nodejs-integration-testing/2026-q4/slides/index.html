Calculated default

When each test spawns its own application process, the ideal concurrency is
half the available parallelism, plus one

concurrency = floor(availableParallelism / 2) + 1
            = floor(12 / 2) + 1
            = 7   // the measured optimum

This might not be perfect, but its a better starting point than max parallelism, and remains configurable

2. Networking contention

Everything wants port 9925

Dynamic ports would mean core changes

The easy fix: let the OS hand out a free port.

server.listen(0, () => {
  const { port } = server.address();   // the OS picked a free one
});

But two problems:

  • The app has to report back which ports it received
  • Harper currently requires ports to be configured

How can we solve this without modifying core?

Not a real fix: get-port

// what get-port does, roughly:
async function getPort() {
  const server = net.createServer();
  await listen(server, 0);          // OS assigns a free port
  const { port } = server.address();
  await close(server);              // ← the port is released here
  return port;
}

const port = await getPort();
const harper = await createHarper(port);   // ← nothing reserved it in between

Between the release and the reuse, the OS can hand that port to any other process — especially with many test processes racing at once.

If we can't reliably reserve the ports…
what about the address?

Introducing loopback addresses

All of 127.0.0.0/8 (127.0.0.1 through 127.255.255.255) loops back to localhost

// every instance keeps its default ports
test/application 1 → http://127.0.0.2:9925
test/application 2 → http://127.0.0.3:9925
test/application 3 → http://127.0.0.4:9925
  • Every instance can use port 9925 without conflict
  • Isolation is by address
Each node binds several fixed ports on its address: 9925 (operations), 9926 (HTTP), 1883 and 8883 (MQTT), and 9927 (HTTPS) when TLS is configured. The harness passes them as address:port, e.g. --HTTP_PORT=127.0.0.2:9926.

One caveat: macOS needs setup

Windows routes all of 127.0.0.0/8 to loopback already: harper's Windows CI shards run with no alias setup. The integration-testing README still says Windows needs setup; that's worth fixing upstream.

macOS: register each address

# once per boot, or install the provided launchd daemon
npx harper-integration-test-setup-loopback

# what it runs for each address in the pool
sudo ifconfig lo0 alias 127.0.0.2 netmask 255.255.255.255 up
The script configures 32 addresses by default (127.0.0.2 to 127.0.0.33; set HARPER_INTEGRATION_TEST_LOOPBACK_POOL_COUNT for more, up to 254), verifies every alias landed, and ships scripts/io.harperdb.loopback-setup.plist so the aliases survive a reboot. macOS drops lo0 aliases on every restart.

Every alias claims the same network

No explicit netmask? macOS assigns /8.

# address     claimed network
127.0.0.2  →  127.0.0.0/8
127.0.0.3  →  127.0.0.0/8
127.0.0.4  →  127.0.0.0/8
  • Each address conflicts with every other.
  • mDNSResponder keeps defending them.
    O(n²) work. A storm of announcements.
That netmask in the setup command matters. Without it, macOS assigns 255.0.0.0, or /8. These are different addresses, but every alias claims the whole 127.0.0.0/8 network. [Step 1] This was diagnosed on a developer machine configured with about 254 aliases. The overlapping interface addresses trigger mDNSResponder's address-conflict defense, PacketRRConflict. [Step 2] Each address conflicts with every other, so the defense work grows quadratically. It floods loopback with mDNS announcements on UDP port 5353 and can pin a CPU core. The busy process is mDNSResponder, not a test worker. Source: HarperFast/integration-testing PR #21, Kris Zyp, July 2026.

/32 removes the overlap

  • 255.255.255.255: each alias claims only itself.
  • Same pool capacity. Same test isolation.

254 aliases. One macOS box. One paired measurement.

NetmaskmDNSResponder CPUUDP 5353 packets / 8 s
/8~65%85
/32~0%5
A /32 is a host netmask. Each alias claims one address, so the subnet claims no longer overlap. The addresses still loop back. Same number of aliases, same isolation. [Step 1] This comparison used 254 aliases on the same macOS machine in the same run. With /8, mDNSResponder measured about 65% CPU and 85 packets over eight seconds on UDP 5353. With /32, about zero CPU and five packets, the observed floor. One measurement, not a cross-machine benchmark. The setup script removes each existing alias before adding it, so re-running it converts old /8 setups to /32. Next: the addresses are configured. How do we assign them to test processes without handing out the same address twice? Source: HarperFast/integration-testing PR #21, Kris Zyp, July 2026.

How do we manage which process gets which address?

Loopback Address Pool: JSON file with an array of PIDs, shared by every test process.

[42, 43, null, 45, null, null]

index 0 → 127.0.0.2 (PID 42) · index 1 → 127.0.0.3 (PID 43) · …

  • Index is the address; value is the owning process ID
  • First-available allocation; released once its ports are free
The PIDs are test runner processes, not Harper. Default pool: 32 addresses. Pool file: $TMPDIR/harper-integration-test-loopback-pool.json.

Cross-process mutex to avoid conflicts

// 'wx' fails if the file already exists — atomically
const handle = await open(LOCK_PATH, 'wx');
await handle.writeFile(token);   // we hold the lock
await handle.close();

One of many options (daemon, orchestrator, atomics).

File lock was simplest. Plus a stale-lock timeout for crashed processes.

The stale timeout is 10 seconds. The token is pid, a counter, and random bytes, so a process can tell its own lock from a successor's.

A slow writer can lose the lock

await writeFile(pendingPath, JSON.stringify(pool));
await assertLockHeld(token);          // still ours?
await rename(pendingPath, POOL_PATH);  // atomic publish

If a write outlasts the stale timeout, another process takes the lock. The token check stops the old writer from overwriting the new claim.

Added Oct 2026 (integration-testing #32 and #33). Writes go to a temp file and are published by rename, so readers never see a torn file. On a lost lock the operation retries from the current pool state, up to 3 times. An unreadable pool file is quarantined for 6 minutes before it's reset, so in-flight reservations aren't wiped. The check narrows the race; it doesn't close it completely.

Crashed tests would leak addresses forever

// signal 0 checks liveness without signalling
try {
  process.kill(pid, 0);       // alive — leave it allocated
} catch {
  loopbackPool[index] = null;  // dead — reclaim it
}

A Ctrl+C mid-run doesn't break the pool

Reaping runs when the pool is full: dead runner PIDs are cleared before waiting for a free slot.

Crashed runners left Harper running

  • Each Harper starts in its own process group
  • A shared monitor reaps groups whose runner died
  • POSIX only; Windows relies on runner cleanup
A SIGKILL'd runner or a cancelled CI job used to leave Harper alive, holding its fixed ports. Since Sep 2026 (integration-testing #30) every instance registers in a cross-process registry, and one monitor per user reaps orphaned or overdue process groups with kill(-pgid).

Allocated is not the same as usable

// bind to port 0 just to prove the address exists
server.listen(0, loopbackAddress, () => {
  server.close(() => resolve(loopbackAddress));
});

1. Verify the whole pool at startup (ensure setup script was run)

2. Verify again per allocation to avoid collisions

Then two more checks before an address is handed out.

A dying node can still hold the address

Harper's HTTP workers bind with SO_REUSEPORT. A new node could share 9926 with an old node's lingering workers and split its connections.

// an exclusive bind fails with EADDRINUSE, even beside an SO_REUSEPORT socket
for (const port of [9925, 9926]) {
  if (await isPortInUseOnAddress(port, address)) skip(address);
}
The conflict canary, added Jun 2026. The common shape: after a kill, Harper's main thread has exited (freeing 9925) but its HTTP workers still hold 9926. The pool releases the poisoned address, skips it for this attempt, and re-probes it later. This detection is Linux-effective; macOS SO_REUSEPORT semantics differ, but macOS doesn't show the silent co-bind, and CI runs on Linux. Teardown also waits up to 5 s for all ports to free before releasing an address.

Some listeners cover every address

A process on 0.0.0.0:9926, like a local Harper, overlaps the whole pool. On macOS and Windows it quietly takes a node's connections.

// an exclusive bind succeeds beside it there, so connect instead
const port = await findAcceptingPort(address, [9925, 9926]);
if (port) throw new ForeignListenerError(address, port);
Added Sep 2026. The foreign process gets the node's connections whenever the node has no listener of its own: while it starts, while HTTP workers restart, and after teardown. Keep-alive connections then stay with it, so a suite fails, or passes, against the wrong server. Linux refuses the exclusive bind, so it skips this probe. Set HARPER_INTEGRATION_TEST_ALLOW_FOREIGN_LISTENERS=1 to turn the error into a warning.

The API is shaping up

3. Framework agnostic

The API imports nothing from a test runner

startHarper(ctx, options?)
setupHarperWithFixture(ctx, fixturePath, options?)
killHarper(ctx)
teardownHarper(ctx)
createHarperContext(name?)   // for non-node:test frameworks

ctx is any object with an optional name and a harper property to write to.

Deliberately loose, so a node:test context and a plain object both satisfy it.

Keep it flexible

// src/run.ts:
// Important! This script should not be required
// to execute integration tests.

https://github.com/HarperFast/integration-testing/blob/main/src/run.ts

The convenience runner (configures a smarter concurrency default) holds no state.

Every test file still runs under plain node --test, and parallelization still works.

4. Surviving CI

How do you think a M3 Macbook compares to a default GitHub CI runner?

One default runner can't run all the tests

Parallelize across runners: a matrix that shards the suite.

# .github/workflows/integration-tests.yml
strategy:
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: node --test --test-shard=${{ matrix.shard }}/4

--test-shard=1/3 always runs the same group of tests, on any machine
https://github.com/HarperFast/harper/blob/main/.github/workflows/integration-tests.yml

node:test also exposes this programmatically: run({ shard: { index, total } }). The groupings are deterministic — shard 1/3 is the same set of files on every machine — so a flake on one shard is reproducible.

CI is not always green

Data and method

Share of main push runs of integration-tests.yml with a failed conclusion. December is left out: the workflow only started running on main when PR #27 merged on Dec 3, so it had just 13 main pushes (all passed). January also had only 13 (one failed). Jan to Apr failures were almost all the legacy suite. Jun to Aug: the matrix grew (Windows, Bun, Node 26, uWS) and Windows had long tail latency. Runs where a Linux Node shard failed: Dec 0%, Jan 0%, Feb 0%, Mar 4%, Apr 0%, May 12%, Jun 40%, Jul 30%, Aug 34%, Sep 10%. October is left out because the month isn't over.

Last 30 days

  • 22% of main runs failed
  • Nearly half of those failed only on Windows, Bun, or uWS
  • Failures include real regressions, like Node 26

Data and method

Sep 23 to Oct 22, 2026: 55 of 253 main runs failed; 11% of runs had a Linux Node shard failure. Failures include real regressions the suite caught, like Node 26: it alone failed 11 to 32 main runs a month and was pinned to 26.5.0 from Aug 3 to Sep 1. Re-runs that turned green: 12.9% in July, 4.3% in September. Re-run-to-green = runs with run_attempt > 1 whose final attempt succeeded, as a share of completed runs. The old and new suites and matrices differ, so this does not show CI became less flaky.
