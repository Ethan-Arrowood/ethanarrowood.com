Treat the application as a black box

Inputs you control
  • Requests & operations
  • Config, env, CLI flags
  • stdin & signals
→
Application internals off-limits
→
Outputs you observe
  • Responses & status
  • Logs, stdout/stderr
  • Files & exit codes

No mocking, no stubbing, no reaching inside. Assert on behavior, never on implementation.

The black box is the mental model for the whole framework: you drive the app only through the surfaces a real user has, and you judge it only by what you can observe from outside. Nothing hooks into internals. That constraint is what makes the tests resemble real usage — and it's why the rest of the talk is about managing a *process* from the outside, not wiring into Harper's guts.

Application = Process

Integration testing an application means managing the lifecycle of the application process

  • Wait for it to be ready
  • Restart it
  • Send signals to it
  • Write to stdin
  • Stream and read stdout and stderr
  • Read and process log files
  • Monitor crashes
  • Stop it
  • Clean up
Applications are a process and testing applications in this scenario means managing that process and all that comes with it.

In Harper's case...

  • Networking & ports
  • A file system and a database on disk
  • Worker threads it spawns to go fast
  • How do we keep everything isolated?
Now beyond just process management, you have to consider everything else involved in an application. Networking, file system, threads. Apps can be complicated!

how much parallelism is actually possible?

Measuring instead of guessing

Concurrency is an overloaded term

Is it the same as parallelism?

How do you actually do multiple things at once in the Node.js event loop?

node:test "concurrency"

Test runner concurrency = file-level process parallelism

node --test \
  --test-concurrency=5 \
  "*.test.js"

Test suite concurrency = in-process async concurrency

suite('x', { concurrency: true }, () => {
  test('a', async () => { … });
  test('b', async () => { … });
});
Answer the setup question directly: these are both called "concurrency," but the first is real parallelism (a child process per file) and the second is just async concurrency on one event loop. The distinction is load-bearing: only the first spawns processes, so only the first contends for CPU, disk, and addresses. If each test file spawns a Harper, that file-level dial is the one that matters — say so aloud; "separate memory, real OS parallelism" vs "Promise.all, not processes."

Node's default is built for cheap tests

// node:test default --test-concurrency
os.availableParallelism()   // 12 on my laptop

If each test process spawns an application process, we realistically only have half the available parallelism.

Be fair to Node here: the default is right for the common case. It's wrong for resource-intensive integration tests. Hypothesis going in: too few is slow, too many causes contention and thrashing.

The experiment

  • 20 generated test files, each starting a simulated application in its own process
  • Work per file randomized within a mode:
    • 0-100 MB file I/O
    • 0-3 processes
    • 0-4 worker threads
  • Concurrency 1 → 12 (sequential to max parallelism)
  • 25 samples per level, on a normal developer laptop

https://github.com/ethan-arrowood/node-test-runner-parallelization-analysis

What I expected, and what I got

Hypothesis

Over-parallelizing causes contention, thrashing, and unpredictable failures.

Measured

Contention and thrashing: yes. Failures: zero — every level, all 25 samples.

Correctness held; the only cost was latency in the tail. So the right default isn't the most parallelism — it's the peak.

Be straight about this. I went in expecting flakiness and the data didn't show any — 80 passed, 0 failed, every level, every sample. Worth saying why: the tests were independent, hermetic, and deterministic by construction. Contention made them slow, not wrong. That's a result about the test design as much as about the runner.

The default we shipped

When each test spawns its own application process, the ideal concurrency is half the available parallelism, plus one.

concurrency = floor(availableParallelism / 2) + 1
            = floor(12 / 2) + 1
            = 7   // the measured optimum

One machine's number, not a universal constant — but a better starting point than max parallelism, and overridable by flag or env var.

Why not just half? Modern machines are good at doing many things at once, so a little contention past the halfway point is still a net win — the peak sits just above half, not at it. Honest caveat: n=1 machine. The heuristic is "roughly half," not literally 7. The basin is wide and flat, so being approximately right is enough, and the override path matters more than the default.

2. Networking contention

Everything wants port 9925

Dynamic ports would mean core changes

The easy fix: let the OS hand out a free port. Two problems:

  • The app has to report back which ports it got
  • Harper requires ports to be configured — no dynamic support

Both would mean changing Harper core — exactly what a testing framework shouldn't demand.

The abstract for this talk says "dynamic port allocation," and this is where I correct myself in public: I tried it, and the config surface plus the core changes made it not worth it. The real insight is on the next slide — the conflict isn't about ports, it's about the address.

Not a real fix: get-port

// sindresorhus/get-port
const port = await getPort();              // claim a port (listen 0), then free it (close)
const harper = await createHarper(port);   // ← nothing reserved it in between

Between the release and the reuse, the OS can hand that port to any other process — especially with many test processes racing at once.

get-port is the standard "find a free port" package, and it's the obvious thing to reach for. The problem is structural, not a bug in the library: proving a port is free (bind then close) is not the same as holding it. The window between close() and the next bind is where the race lives.

If we can't deterministically reserve/configure the ports,
what about the address?

Beat. This is the idea I most want people to take home, because it generalizes to anything that binds well-known ports.

Introducing loopback addresses

All of 127.0.0.0/8 — 127.0.0.1 through 127.255.255.255 — loops back to your own machine.

// every instance keeps its default ports
worker 1 → http://127.0.0.2:9925
worker 2 → http://127.0.0.3:9925
worker 3 → http://127.0.0.4:9925
  • 16.7 million addresses, all localhost
  • You assign them — the OS never hands them out at random, so nothing to compete over
  • Every instance keeps port 9925; isolation is by address, not port bookkeeping
A /8 means the first octet (127) is fixed and the remaining 24 bits are free — that's the 16.7M. The whole block is reserved for loopback, so any 127.x.y.z routes straight back to this host, never the network. We use 32 by default, starting at .2 so we never fight whatever the developer already has bound to 127.0.0.1. The trade: a little platform setup cost, in exchange for deleting an entire category of configuration.

One caveat: only Linux enables by default

# macOS: register each address as a loopback alias (once per machine)
sudo ifconfig lo0 alias 127.0.0.2 up
sudo ifconfig lo0 alias 127.0.0.3 up
# …a setup script does this for the whole pool
Don't hide this. It's the main objection to the approach and it deserves a straight answer: on macOS/Windows each address is a one-time alias, and the setup script (npx harper-integration-test-setup-loopback, needs sudo) just loops the ifconfig call across the pool. Once, per machine, and it's in the setup docs and the CI workflow. Sequential mode (--isolation=none) skips the requirement entirely, which matters for a contributor who just wants to run one test.

How do we manage which process gets which address?

A JSON file in tmpdir() — an array of PIDs, shared by every test process.

// pool.json — index → address, value → owning PID
[42, 43, null, 45, null, null]

index 0 → 127.0.0.2 · index 1 → 127.0.0.3 · …

  • Index is the address; value is the owning process ID
  • First-available allocation; released on teardown
Storing the PID rather than a boolean is what makes recovery possible — see the next slide but one. Why a file and not a coordinating parent process? The runner script must be optional: tests have to work under plain `node --test`, with no parent to coordinate them. Honest limit: this only coordinates test-runner processes. Another app on the machine could still grab an address — far less common, and you can avoid it by not racing other servers while tests run.

Cross-process mutex in one flag

// 'wx' fails if the file already exists — atomically
const handle = await open(LOCK_PATH, 'wx');
await handle.close();   // we hold the lock

The file system already has the primitive — no dependency, no daemon.

One of many options (daemon, orchestrator, atomics); a file lock was simplest. Plus a stale-lock timeout, since a crashed process can't unlink its own lock.

The job is just "one process touches the pool at a time." `wx` is O_CREAT | O_EXCL — the atomicity guarantee comes from the kernel. Many ways to solve this; a file lock was the most familiar and got the job done. The stale timeout is the unglamorous half. Every file-lock scheme needs one, and picking it is a judgment call: too short and you break a slow-but-live process, too long and a crash stalls the suite.

Crashed tests would leak addresses forever

// signal 0 checks liveness without signalling
try {
  process.kill(pid, 0);       // alive — leave it allocated
} catch {
  loopbackPool[index] = null;  // dead — reclaim it
}

A Ctrl+C mid-run costs you nothing next time.

This is why the pool stores PIDs instead of booleans — a boolean pool can't distinguish "in use" from "leaked." Reaped lazily, only when the pool looks full: reaping on every allocation would mean a syscall per slot for a condition that's almost never true.

Allocated is not the same as usable

// bind to port 0 just to prove the address exists
server.listen(0, loopbackAddress, () => {
  server.close(() => resolve(loopbackAddress));
});

Verified twice: for the whole pool at startup — with an error that names the setup script — and again per allocation.

Still not immune to another app grabbing the address first, but loopback allocation collides far less often than dynamic ports.

Remember the racey dynamic allocation issue? Well we can actually use that to our advantage here to at least check that the address is usable. The failure this prevents is the worst kind: Harper starts, binds nothing, and the test times out 30 seconds later with a message about HTTP. Fail at allocation instead, and say which command fixes it. Good error messages are a feature of test infrastructure, not a polish item. A confused contributor is a contributor who stops running tests.

What a test actually gets

await startHarper(ctx);
// 1. allocate a loopback address from the pool
// 2. create a temporary install directory
// 3. spawn Harper, wait until it is actually ready
// 4. populate ctx.harper

ctx.harper.httpURL            // 'http://127.0.0.3:9926'
ctx.harper.operationsAPIURL   // 'http://127.0.0.3:9925'

await teardownHarper(ctx);
// kill, release the address, remove the directory
Temporary install directory per instance is the other half of isolation — address isolation without filesystem isolation still gives you two processes fighting over one data root. "Wait until actually ready" is doing a lot of work. Spawning is not readiness, and a 30-second startup timeout with captured stdout/stderr is what makes a startup failure diagnosable.

Replication used to need a data center

The old way

  • Five Harper containers on a Docker network, or five VMs
  • Cluster env vars, IPs, and DNS templated in by hand
  • Driven by Postman collections in bespoke CI jobs

Now

  • N in-process instances from the same loopback pool
  • Connected with a plain add_node operation
  • Write to one node, assert it lands on the others

Parallelism was the goal. The bonus: a node dying and catching up, mesh vs. star topology, even migrating off a legacy 4.x node — all in ordinary, parallel node:test files.

This is the emotional peak. Call back to the opening: those Postman collections gating the old suite? The cluster tests were the worst of it — five containers on a network before you could assert a single write replicated. The reframe: the loopback pool wasn't just a speed trick. The moment many real instances can coexist on one machine, an entire class of features that used to demand infrastructure — replication, failover, topology — becomes a plain integration test you can run on a laptop. Real files in harper-pro: fullyConnectedReplication (4-node mesh), replicationTopology (star, kill-and-catch-up, 4.x migration), replicationLoad (stress across many databases).

A cluster is N instances plus add_node

// a cluster is N instances, each on its own loopback address
const nodes = await Promise.all(
  Array(4).fill().map(async () => {
    const ctx = { harper: { hostname: await getNextAvailableLoopbackAddress() } };
    await startHarper(ctx, { config: replicationConfig });
    return ctx.harper;
  })
);
// connect each node to node 0, then write here and read there
for (const node of nodes.slice(1))
  await sendOperation(node, { operation: 'add_node', hostname: nodes[0].hostname });
await sendOperation(nodes[0], { operation: 'upsert', table: 'dog', records: [dog] });
const res = await sendOperation(nodes[1], { operation: 'search_by_id', ids: ['1'] });
strictEqual(res[0].name, 'Harper');

No cluster helper. Start the single instance N times and wire the nodes with normal operations; the framework's one job is handing out conflict-free addresses.

Simplified from harper-pro's fullyConnectedReplication test. The real code sets a per-node replication securePort on that node's own loopback address, and the write passes replicatedConfirmation: N-1 so the read is deterministic rather than racing propagation — worth mentioning aloud, cut here for space. The honest point in the caption matters: the framework didn't grow a cluster abstraction. It stayed small, and the loopback pool from the last section is the only thing that makes N conflict-free instances possible. add_node is an ordinary Harper operation.

3. Framework agnostic

The constraint that keeps the rest honest

The API imports nothing from a test runner

startHarper(ctx, options?)
setupHarperWithFixture(ctx, fixturePath, options?)
killHarper(ctx)
teardownHarper(ctx)
createHarperContext(name?)   // for non-node:test frameworks

ctx is any object with an optional name and a harper property to write to.

Deliberately loose, so a node:test context and a plain object both satisfy it.

The type is the whole trick. If the signature demanded a node:test TestContext, Playwright could never call it. Requirement on any framework: async setup and teardown hooks. That's it. Every runner has them.

The rule that made it possible

"Important! This script should not be required to execute integration tests."

— the first line of src/run.ts

The convenience runner holds no state. Every test file still runs under plain node --test, and parallelization still works.

This is the design decision everything else follows from. Because the runner couldn't own setup, setup had to live in the test files, which forced the pool to be file-based and cross-process rather than parent-coordinated. The constraint that looked like a limitation is what made the second framework integration cheap.

Two runners, same lifecycle

node:test — file per process

suite('install', (ctx: ContextWithHarper) => {
  before(async () => {
    await startHarper(ctx);
  });
  after(async () => {
    await teardownHarper(ctx);
  });

  test('serves', async () => {
    const res = await fetch(ctx.harper.httpURL);
    strictEqual(res.status, 200);
  });
});

Playwright — worker-scoped fixture

const test = base.extend<
  {}, { harper: HarperContext }
>({
  harper: [makeHarperFixture(name),
           { scope: 'worker' }],
});

test('home page renders',
  async ({ page, harper }) => {
    await page.goto(harper.httpURL);
    await expect(page.locator('h1'))
      .toHaveText('Next.js v16');
  });
Left is @harperfast/integration-testing's own template. Right is real code from @harperfast/nextjs, testing the Next.js plugin. The mapping to draw out loud: a node:test *file process* and a Playwright *worker* play the same role. Both are the unit that owns one Harper instance.

The entire Playwright integration

export function makeHarperFixture(fixtureName: string) {
  return async ({}, use) => {
    const ctx = createHarperContext(fixtureName);
    const started = await setupHarperWithFixture(ctx, fixturePath, {
      harperBinPath: getHarperBinPath(),
      startupTimeoutMs: 120_000,   // a Next.js build is slow
    });

    await use(started.harper);

    await teardownHarper(started);
  };
}

~40 lines including error handling. The pool, the locking, and the address assignment are all inherited for free.

This is the payoff slide for the whole framework-agnostic argument. The second integration cost an afternoon, not a rewrite. Note what isn't here: no ports, no coordination between workers, no knowledge that other workers exist.

What the framework won't decide for you

  • Each instance costs a process, an address, a directory
  • Per logical test block: usually right
  • Per assertion: almost always wasteful
  • Concurrent scopes need separate instances — the one hard rule

The pool makes allocation safe. Your hooks pick the boundaries.

Deliberately not automated. Instance scope is a judgment call about what a test means, and a framework that guessed would guess wrong. The Playwright config makes this choice explicitly: fullyParallel: false, so files run in parallel but tests within a file share the worker's instance and run in order.

None of this works without disciplined tests

  • Independent — no dependence on order or shared state
  • Hermetic — self-contained, no external side effects
  • Deterministic — same input, same output

Not style — the precondition for safe concurrency, and why 25 samples at every level had zero failures.

Tie back to the honesty slide. The reason over-parallelizing cost latency and not correctness is that the tests obeyed these three properties. Without them, parallelization doesn't get slower. It gets flaky, which is much worse and much harder to debug.

4. Surviving CI

Where the laptop assumptions break

Default runners can't take the parallelism

  • One integration test per runner: fine. Many: it buckles
  • Overloaded runners go flaky — never trade correctness for speed
  • So parallelize across runners: matrix + sharding
npm run test:integration -- --shard=1/4   # one job per shard
Same lesson as the concurrency curve, one level up: the constrained resource moved from cores to runners, and the answer is still "don't oversubscribe." Bigger runners exist. They cost real money, and org-level job caps mean queue time can eat the savings — measure before buying.

And be deliberate about when

  • Full matrix on every PR commit exhausts your limits
  • Path filters, manual triggers, merge-time-only full runs
  • Merge queue: the whole matrix, once, before merge

Fast on the PR, thorough on the branch that matters.

This is the pragmatic close on CI: the cheapest optimization is not running the suite when it can't tell you anything new.

What to take home

  1. Measure your concurrency ceiling. For process-heavy tests it's near half your cores, not all of them.
  2. Watch the tail, not the mean. Over-parallelizing buys variance.
  3. Isolate by address, not by port. One loopback address per instance deletes a config matrix.
  4. The file system has your mutex. open(path, 'wx') plus a stale timeout.
  5. Make the runner optional. That constraint is what buys you the second framework.
Five points, and only 1, 3, and 5 really need to land. If the timer is red, read 1, 3, 5 and go to the last slide.
