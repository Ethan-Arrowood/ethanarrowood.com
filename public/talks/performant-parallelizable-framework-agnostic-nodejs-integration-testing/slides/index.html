Performant, Parallelizable, Framework Agnostic Node.js Integration Testing

Testing is hard

"It works on my machine."

"That test's just flaky, re-run it."

"You can't run those locally."

"It only runs in CI."

"Don't touch it! It's finally green."

Read a couple aloud and let them land, then the line: "I'm sure we've all heard or felt these before. I know I sure have." Then pivot — this was our reality a few years ago; it isn't now.

What am I testing?

github.com/HarperFast/harper github.com/HarperFast/harper-pro

One process contains:

  • Database
  • Networking stack (socket, HTTP, WS, etc.)
  • File System & Blobs
  • Applications and plugins
  • Worker threads for parallelism
This is a collapsed stack — the deployment story is "one process," which is great for operators and awkward for testers. Don't sell Harper here. The audience needs exactly enough to understand why the testing problem is shaped the way it is.

What "integration" means here

Unit

A slice of code, in isolation. Mocks and stubs are fine. Fast, but it can't see the system.

Integration

The complete, built application running in CI, a container, or on your laptop.

End-to-end

Deployed to production-like infrastructure

"Integration test" means five different things to five people, so define it before building on it. Mine: run the built app, treat it as a black box, interact only through the surfaces a user has. No reaching into source. That constraint is what makes the tests resemble real usage — and it's a deliberate design decision, not an accident of tooling.

Why a collapsed stack resists integration testing

Conventional service

  • Mock the database
  • Mock the queue
  • Boot the app in-process
  • Tests are cheap and parallel by default

Harper

  • The database is the thing under test
  • So is the network layer, and the CLI
  • A real test needs a real Harper process
  • Tests are expensive and conflict by default
The key line: you cannot mock the thing you are trying to test. Every seam a conventional service would mock is inside the system boundary here. So the unit of isolation is a process, not a fixture.

Every test needs its own process.
Now make it fast.

This is the whole talk in one slide. Pause here.

Four constraints

  1. Parallelize — but each test owns a heavyweight process
  2. Don't collide — every instance wants the same ports
  3. Run anywhere — three operating systems, laptops and CI
  4. Don't marry a runner — node:test for APIs, Playwright for browsers
These four are the talk's structure. Each one gets a section. Say explicitly: constraint 4 is the one that most teams skip, and it's the one that determines whether the other three stay solved.

1. How parallel is too parallel?

Measuring instead of guessing

Two things called "concurrency"

File parallelism — real

node --test \
  --test-concurrency=5 \
  "*.test.js"

Each file gets its own child process. Separate memory, real OS parallelism.

Test concurrency — async

suite('x', { concurrency: true }, () => {
  test('a', async () => { … });
  test('b', async () => { … });
});

One event loop. Promise.all, not processes.

These get conflated constantly, and the distinction is load-bearing for the rest of the talk: only the left one spawns processes, so only the left one contends for CPU, disk, and addresses. If each test file spawns a Harper, file parallelism is the dial that matters.

Node's default is built for cheap tests

// node:test default --test-concurrency
os.availableParallelism()   // 12 on my laptop

Reasonable for unit tests. For twelve simultaneous database processes, it is a guess — so I measured it.

Be fair to Node here: the default is right for the common case. The claim is narrower — it's wrong for resource-intensive integration tests. Hypothesis going in: too few is slow, too many causes contention and thrashing.

The experiment

  • 20 generated test files, each starting a simulated application in its own process
  • Work per file randomized within a mode — 0–100 MB file I/O, 0–3 processes, 0–4 worker threads
  • Concurrency swept 1 → 12 (sequential to max parallelism)
  • 25 samples per level, on a normally-used laptop

Optimizing for developer experience, not benchmark numbers — nobody stops using their machine while tests run.

Modes matter: in a real suite one file does far more work than the next. A fixed workload would have produced a cleaner graph and a less useful answer. Call out the "normally-used laptop" choice. Maximum parallelism wins on an idle machine, and an idle machine is not a thing developers have.

Developers don't experience your median. They experience the run they're waiting on.

This is the slide I'd keep if I had to cut the section to one. Over-parallelizing doesn't make the suite slower on average so much as it makes it *unpredictable*, and unpredictable is what makes people stop trusting a suite.

What I expected, and what I got

Hypothesis

Over-parallelizing causes resource contention, thrashing, and unpredictable failures.

Measured

Contention and thrashing: yes. Failures: zero, at every concurrency level, in all 25 samples.

Correctness held. The cost showed up entirely in the tail.

Be straight about this. I went in expecting flakiness and the data didn't show any — 80 passed, 0 failed, every level, every sample. Worth saying why: the tests were independent, hermetic, and deterministic by construction. Contention made them slow, not wrong. That's a result about the test design as much as about the runner.

So this became the default

// @harperfast/integration-testing — src/run.ts
const CONCURRENCY = concurrencyOption
  ? parseInt(concurrencyOption, 10)
  : Math.max(1, Math.floor(availableParallelism() / 2) + 1);

floor(12 / 2) + 1 = 7 — the measured optimum on the machine the measurements came from.

Half of available parallelism, plus one. Overridable by flag or environment variable, because your workload isn't mine.

Honest caveat: n=1 machine. The heuristic is "roughly half," not "7." The shape of the curve is what generalizes — the basin is wide and flat, so being approximately right is enough. The override path matters more than the default. Someone on a 96-core CI box with light tests should turn it up.

2. Two databases, one machine

Everything wants port 9925

The obvious fix, and why I skipped it

Dynamic port allocation: ask the OS for a free port, hand it to the instance.

Except one Harper instance doesn't bind a port:

  • Operations API — 9925
  • HTTP / application server — 9926
  • Replication, clustering, and more

Remapping all of them, per instance, means threading a config matrix through every test — and every URL in every assertion.

The abstract for this talk says "dynamic port allocation," and this is where I correct myself in public: I tried it, and the config surface made it not worth it. The insight is that the conflict isn't really about ports. It's about the address you bind them to.

Don't change the ports.
Change the address.

Beat. This is the idea I most want people to take home, because it generalizes to anything that binds well-known ports.

One loopback address per instance

// every instance keeps its default ports
worker 1 → http://127.0.0.2:9925
worker 2 → http://127.0.0.3:9925
worker 3 → http://127.0.0.4:9925
  • Zero config remapping — 9925 is still 9925
  • 127.0.0.0/8 is 16.7 million addresses
  • Instances are isolated by address, not by port bookkeeping
The whole loopback /8 belongs to localhost. We use 32 by default, starting at .2 so we never fight whatever the developer already has bound to 127.0.0.1. This is the trade: a little platform setup cost, in exchange for deleting an entire category of configuration.

The catch: only Linux gives them to you

npx harper-integration-test-setup-loopback   # needs sudo

A one-time, per-machine cost — and the honest price of this design.

Don't hide this. It's the main objection to the approach and it deserves a straight answer: it's one command, once, per machine, and it's in the setup docs and the CI workflow. Sequential mode (--isolation=none) skips the requirement entirely, which matters for a contributor who just wants to run one test.

The pool is a JSON array of PIDs

42 43 null 45 null null

index 0 → 127.0.0.2 · index 1 → 127.0.0.3 · …

  • Index is the address; value is the owning process ID
  • Lives in tmpdir(), so every test process shares it
  • First-available allocation; released on teardown
Storing the PID rather than a boolean is what makes recovery possible — see the next slide but one. Why a file and not a coordinating parent process? Because of the constraint on the runner script: tests must work under plain `node --test`, with no parent to coordinate them.

Cross-process mutex in one flag

// 'wx' fails if the file already exists — atomically
const handle = await open(LOCK_PATH, 'wx');
await handle.close();   // we hold the lock

No dependency, no daemon, no shared memory. The file system already has the primitive.

Plus a stale-lock timeout: a lock file older than 10 seconds is assumed abandoned and removed — because a crashed test process cannot unlink its own lock.

`wx` is O_CREAT | O_EXCL. The atomicity guarantee comes from the kernel. The stale timeout is the unglamorous half. Every file-lock scheme needs one, and picking the timeout is a judgment call: too short and you break a slow-but-live process, too long and a crash stalls the suite.

Crashed tests would leak addresses forever

// signal 0 checks liveness without signalling
try {
  process.kill(pid, 0);       // alive — leave it allocated
} catch {
  loopbackPool[index] = null;  // dead — reclaim it
}

Reaped lazily, only when the pool looks full. A Ctrl+C mid-run costs you nothing on the next run.

This is why the pool stores PIDs instead of booleans. A boolean pool can't distinguish "in use" from "leaked." Lazily, not eagerly: reaping on every allocation would mean a syscall per slot per allocation for a condition that's almost never true.

Allocated is not the same as usable

// bind to port 0 just to prove the address exists
server.listen(0, loopbackAddress, () => {
  server.close(() => resolve(loopbackAddress));
});

Verified twice: once for the whole pool at startup — with an actionable error naming the setup script — and once per allocation.

The failure this prevents is the worst kind: Harper starts, binds nothing, and the test times out 30 seconds later with a message about HTTP. Fail at allocation instead, and say which command fixes it. Good error messages are a feature of test infrastructure, not a polish item. A confused contributor is a contributor who stops running tests.

What a test actually gets

await startHarper(ctx);
// 1. allocate a loopback address from the pool
// 2. create a temporary install directory
// 3. spawn Harper, wait until it is actually ready
// 4. populate ctx.harper

ctx.harper.httpURL            // 'http://127.0.0.3:9926'
ctx.harper.operationsAPIURL   // 'http://127.0.0.3:9925'

await teardownHarper(ctx);
// kill, release the address, remove the directory
Temporary install directory per instance is the other half of isolation — address isolation without filesystem isolation still gives you two processes fighting over one data root. "Wait until actually ready" is doing a lot of work. Spawning is not readiness, and a 30-second startup timeout with captured stdout/stderr is what makes a startup failure diagnosable.

Replication used to need a data center

The old way

  • Five Harper containers on a Docker network, or five VMs
  • Cluster env vars, IPs, and DNS templated in by hand
  • Driven by Postman collections in bespoke CI jobs

Now

  • N in-process instances from the same loopback pool
  • Connected with a plain add_node operation
  • Write to one node, assert it lands on the others

Parallelism was the goal. The bonus: a node dying and catching up, mesh vs. star topology, even migrating off a legacy 4.x node — all in ordinary, parallel node:test files.

This is the emotional peak. Call back to the opening: those Postman collections gating the old suite? The cluster tests were the worst of it — five containers on a network before you could assert a single write replicated. The reframe: the loopback pool wasn't just a speed trick. The moment many real instances can coexist on one machine, an entire class of features that used to demand infrastructure — replication, failover, topology — becomes a plain integration test you can run on a laptop. Real files in harper-pro: fullyConnectedReplication (4-node mesh), replicationTopology (star, kill-and-catch-up, 4.x migration), replicationLoad (stress across many databases).

A cluster is N instances plus add_node

// a cluster is N instances, each on its own loopback address
const nodes = await Promise.all(
  Array(4).fill().map(async () => {
    const ctx = { harper: { hostname: await getNextAvailableLoopbackAddress() } };
    await startHarper(ctx, { config: replicationConfig });
    return ctx.harper;
  })
);
// connect each node to node 0, then write here and read there
for (const node of nodes.slice(1))
  await sendOperation(node, { operation: 'add_node', hostname: nodes[0].hostname });
await sendOperation(nodes[0], { operation: 'upsert', table: 'dog', records: [dog] });
const res = await sendOperation(nodes[1], { operation: 'search_by_id', ids: ['1'] });
strictEqual(res[0].name, 'Harper');

No cluster helper. Start the single instance N times and wire the nodes with normal operations; the framework's one job is handing out conflict-free addresses.

Simplified from harper-pro's fullyConnectedReplication test. The real code sets a per-node replication securePort on that node's own loopback address, and the write passes replicatedConfirmation: N-1 so the read is deterministic rather than racing propagation — worth mentioning aloud, cut here for space. The honest point in the caption matters: the framework didn't grow a cluster abstraction. It stayed small, and the loopback pool from the last section is the only thing that makes N conflict-free instances possible. add_node is an ordinary Harper operation.

3. Framework agnostic

The constraint that keeps the rest honest

The API imports nothing from a test runner

startHarper(ctx, options?)
setupHarperWithFixture(ctx, fixturePath, options?)
killHarper(ctx)
teardownHarper(ctx)
createHarperContext(name?)   // for non-node:test frameworks

ctx is any object with an optional name and a harper property to write to.

Deliberately loose, so a node:test context and a plain object both satisfy it.

The type is the whole trick. If the signature demanded a node:test TestContext, Playwright could never call it. Requirement on any framework: async setup and teardown hooks. That's it. Every runner has them.

The rule that made it possible

"Important! This script should not be required to execute integration tests."

— the first line of src/run.ts

The convenience runner holds no state. Every test file still runs under plain node --test, and parallelization still works.

This is the design decision everything else follows from. Because the runner couldn't own setup, setup had to live in the test files, which forced the pool to be file-based and cross-process rather than parent-coordinated. The constraint that looked like a limitation is what made the second framework integration cheap.

Two runners, same lifecycle

node:test — file per process

suite('install', (ctx: ContextWithHarper) => {
  before(async () => {
    await startHarper(ctx);
  });
  after(async () => {
    await teardownHarper(ctx);
  });

  test('serves', async () => {
    const res = await fetch(ctx.harper.httpURL);
    strictEqual(res.status, 200);
  });
});

Playwright — worker-scoped fixture

const test = base.extend<
  {}, { harper: HarperContext }
>({
  harper: [makeHarperFixture(name),
           { scope: 'worker' }],
});

test('home page renders',
  async ({ page, harper }) => {
    await page.goto(harper.httpURL);
    await expect(page.locator('h1'))
      .toHaveText('Next.js v16');
  });
Left is @harperfast/integration-testing's own template. Right is real code from @harperfast/nextjs, testing the Next.js plugin. The mapping to draw out loud: a node:test *file process* and a Playwright *worker* play the same role. Both are the unit that owns one Harper instance.

The entire Playwright integration

export function makeHarperFixture(fixtureName: string) {
  return async ({}, use) => {
    const ctx = createHarperContext(fixtureName);
    const started = await setupHarperWithFixture(ctx, fixturePath, {
      harperBinPath: getHarperBinPath(),
      startupTimeoutMs: 120_000,   // a Next.js build is slow
    });

    await use(started.harper);

    await teardownHarper(started);
  };
}

~40 lines including error handling. The pool, the locking, and the address assignment are all inherited for free.

This is the payoff slide for the whole framework-agnostic argument. The second integration cost an afternoon, not a rewrite. Note what isn't here: no ports, no coordination between workers, no knowledge that other workers exist.

What the framework won't decide for you

  • Starting an instance has real cost — a process, an address, a directory
  • One instance per logical test block: usually right
  • One instance per assertion: almost always wasteful
  • The only hard rule: concurrent scopes need separate instances

The pool makes cross-process allocation safe. Your setup and teardown hooks decide the boundaries.

Deliberately not automated. Instance scope is a judgment call about what a test means, and a framework that guessed would guess wrong. The Playwright config makes this choice explicitly: fullyParallel: false, so files run in parallel but tests within a file share the worker's instance and run in order.

None of this works without disciplined tests

  • Independent — no dependence on order or shared state
  • Hermetic — self-contained, no external side effects
  • Deterministic — same input, same output

These aren't style preferences. They are the precondition for safe concurrency — and the reason 25 samples at every concurrency level produced zero failures.

Tie back to the honesty slide. The reason over-parallelizing cost latency and not correctness is that the tests obeyed these three properties. Without them, parallelization doesn't get slower. It gets flaky, which is much worse and much harder to debug.

4. Surviving CI

Where the laptop assumptions break

Default runners can't take the parallelism

  • A standard GitHub runner handles one integration test fine — and buckles running many
  • Overloaded runners cause flaky failures; correctness is never traded for speed
  • So parallelize across runners: matrix jobs plus test sharding
npm run test:integration -- --shard=1/4   # one job per shard
Same lesson as the concurrency curve, one level up: the constrained resource moved from cores to runners, and the answer is still "don't oversubscribe." Bigger runners exist. They cost real money, and org-level job caps mean queue time can eat the savings — measure before buying.

And be deliberate about when

  • Full matrix on every commit of every PR exhausts concurrency limits
  • Path filters, manual triggers, and merge-time-only full runs
  • Merge queue: one configuration per PR, the whole matrix before merge

Fast iteration on the PR, thorough verification on the branch that matters.

This is the pragmatic close on CI: the cheapest optimization is not running the suite when it can't tell you anything new.

What to take home

  1. Measure your concurrency ceiling. For process-heavy tests it's near half your cores, not all of them.
  2. Watch the tail, not the mean. Over-parallelizing buys variance.
  3. Isolate by address, not by port. One loopback address per instance deletes a config matrix.
  4. The file system has your mutex. open(path, 'wx') plus a stale timeout.
  5. Make the runner optional. That constraint is what buys you the second framework.
Five points, and only 1, 3, and 5 really need to land. If the timer is red, read 1, 3, 5 and go to the last slide.
